## Методика и целостность

- Скрипт: [scripts/load-test.mjs](../scripts/load-test.mjs). Node.js `fetch`, без SDK-повторов, timeout одного запроса 10 секунд. У каждого клиента один запрос в работе, пауза 150 мс между чтениями. При пяти подряд HTTP-ошибках выдача следующей нагрузки прекращается; текущие операции завершаются до очистки.
- Это закрытая модель нагрузки: замедление ответов снижает частоту новых запросов. Она не определяет предельную пропускную способность и может недооценивать задержки при фиксированном внешнем потоке запросов. Определения моделей: [Grafana k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).
- Продолжительная ступень: 240 запросов на каждого из 10 клиентов. Здесь получилась 65,5 секунды чтения; это не многочасовой soak-тест.
- Три предварительно авторизованные учётные записи: постановщик и два исполнителя. Параллельные клиенты переиспользуют эти сессии; это не 25 уникальных аккаунтов. Массовый вход не тестировался.
- Отдельный временный объект, 100 задач локально / 20 в облаке, описания по 500 символов. Читаются объект, его задачи и история одной задачи; выдача проверяется по роли. Это ограниченный набор с фильтрами, не база на десятки тысяч задач.
- Десять независимых задач одновременно проходят `new → in_progress → review → accepted`. Для каждой проверены четыре события истории.
- Отдельно десять запросов одновременно переводят **одну** задачу с одной версией. В каждом из трёх прогонов: **1 успех + 9 ожидаемых HTTP 409**, версия стала 2, событий истории ровно 2. Конфликты не считаются неожиданными ошибками.
- После теста временные объекты и задачи скрыты штатной функцией удаления; история сохранена согласно модели приложения. Демообъекты не изменяются.
- Время запроса измеряется от вызова `fetch` до чтения тела, включая клиентские сетевые расходы. Это не чистое время SQL. Генератор нагрузки — одна Windows-машина; облачный проект — `eu-central-1`. Локальный Docker разделяет ресурсы с генератором и браузером.

## Воспроизведение

```bash
# Docker / Supabase запущены, local-env и seed уже выполнены
npm run test:load

# PowerShell: облачный прогон с публичным ключом и тестовыми аккаунтами
$env:LOAD_ENV_FILE='.env.access'
npm run test:load -- --remote
npm run test:load -- --remote --sustained
Remove-Item Env:LOAD_ENV_FILE
```

Для другого окружения подготовьте приватный env-файл: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, пары `MANAGER_EMAIL/PASSWORD`, `EXECUTOR_EMAIL/PASSWORD`, `SECOND_EXECUTOR_EMAIL/PASSWORD`. Административный ключ не нужен. Для облака обязателен явный `--remote`.

Сырые длительности и статусы записываются в `artifacts/load-*.json` без токенов и паролей. Сводки выполненных запусков сохранены в [performance-results.json](performance-results.json). Код завершения 1 означает провал порога, проверки данных или очистки. Нагрузка запускается отдельно, не автоматически против облака при каждом commit.

## Что эти результаты не доказывают

Не измерялись предел мощности, многочасовая стабильность, холодный старт/возобновление Supabase, большие таблицы, браузерная отрисовка под нагрузкой, Web Vitals, CDN GitHub Pages, массовый login, расход CPU/памяти сервера и нагрузка из нескольких регионов. Пиковая скорость короткого пакета записей не является заявленной производительностью приложения.

Выявленное архитектурное ограничение остаётся прежним: клиентские списки ограничены 1000 строками; пагинации нет. До масштабирования нужны серверные фильтры/пагинация, отдельные агрегаты счётчиков объектов, тестовые данные целевого объёма и повторные замеры с серверной телеметрией.
