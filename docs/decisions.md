# Решения и допущения

1. **Одна компания.** Все постановщики видят все её данные. Это не многопользовательский SaaS для нескольких компаний; изоляцию компаний при необходимости нужно добавить отдельно.
2. **Роль задаёт администратор.** Она хранится в `profiles`, а не в редактируемых пользователем данных аккаунта. Регистрация отключена в локальном Auth и в скрипте настройки облака.
3. **Объекты для исполнителя.** Доступны только объекты, где есть хотя бы одна его неудалённая задача. Принятые задачи тоже учитываются. Название объекта не открывает доступ к задачам коллег.
4. **Редактирование задачи.** Постановщик меняет название, описание и исполнителя в любом статусе. Объект, автор и дата создания закреплены при создании. Перенос задачи между объектами не добавлен. Переназначение не меняет статус; старый исполнитель сразу теряет доступ при следующем запросе.
5. **История.** Записывается создание `— → Новая` и каждый переход статуса. История правок названия, описания и назначения не входила в ТЗ. Все комментарии, кроме обязательного возврата, необязательны. Максимум 2000 символов.
6. **Удаление логическое.** Удаление объекта скрывает также его задачи, история остаётся в базе. Восстановление в интерфейсе не предусмотрено. Администратор базы имеет доступ к архиву; обычный API-пользователь — нет.
7. **Каталог сотрудников.** Авторизованные пользователи видят имена и роли коллег для отображения автора/исполнителя и истории. Email и данные Auth не раскрываются. Чужие задачи закрыты RLS.
8. **Конкурентность.** У каждой записи есть версия. Смена статуса блокирует строку на время транзакции; устаревшая версия отклоняется. Удаление объекта и создание задачи блокируют родительский объект, чтобы не оставлять доступную задачу в удалённом объекте.
9. **Обновление экрана.** Данные перечитываются после действия, при возврате в окно и повторном открытии экрана. Realtime и фоновые уведомления не требуются для данного объёма; не добавлены. Серверная проверка версии работает независимо от свежести интерфейса.
10. **Объём данных.** Интерфейс рассчитан на небольшую CRM: до 1000 строк в запросе. Серверная пагинация, вложения, сроки, поиск по описанию, экспорт и управление аккаунтами через UI не входят в MVP.
11. **Дизайн.** Визуальные ориентиры: [публичный сайт Finleo](https://finleo.ru/) и [форма входа кабинета](https://crm.finleo.ru/), просмотрены 03.11.2026. Светлая рабочая поверхность, нейтральная типографика, один фиолетовый акцент, компактные списки. Логотипы, тексты и бренд Finleo не копируются; функциональность определяется исходным ТЗ.
12. **Граница безопасности.** RLS и SQL-функции защищают от обычных клиентов API. Администратор PostgreSQL и обладатель `service_role` обладают административными полномочиями; их ключи нельзя отдавать пользователям.

Технические ориентиры: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [security-definer функции](https://supabase.com/docs/guides/database/functions), [Playwright webServer](https://playwright.dev/docs/test-webserver).
