# Security review — 03.11.2026

Отдельный проход self-review и целевых атак на собственный тестовый проект. Это не независимый пентест, не гарантия отсутствия всех уязвимостей и не проверка всей инфраструктуры Supabase.

## JWT и сессии

- В локальной конфигурации и облачном Auth закреплён срок **900 секунд / 15 минут** для новых access JWT. Скрипт деплоя проверяет ответ настроек; API-тест проверяет `exp - iat === 900` у реально выданного токена.
- Refresh-токены ротируются, допустимое окно повторного использования — 10 секунд для сетевых повторов. Клиент явно использует автоматическое обновление. Истечение access JWT не означает принудительный выход каждые 15 минут: при действительном refresh-токене сервер выдаёт новую пару.
- Локально проверен **корректно подписанный, но просроченный** JWT: чтение и запись отклонены HTTP 401. Положительный контроль с тем же локальным ключом принят сервером, поэтому тест проверяет именно `exp`, а не случайно неверную подпись. Для этого из локального Docker считывается одноразовый dev-ключ; облачные приватные ключи не извлекаются, ключи и токены в отчёты не записываются.
- Локально и в облаке отклонены JWT без подписи и JWT с изменёнными ролью/сроком, но старой подписью. Расшифровка payload на клиенте не является проверкой подлинности; подпись и срок проверяет API.
- Реальный запрос refresh возвращает новый refresh-токен. После выхода **этой** тестовой сессии её refresh больше не принимается; остальные пользовательские сессии не отзываются.
- Браузерный тест проверяет восстановление при истёкшем `expires_at` в локальном кеше через настоящий refresh endpoint. При недействительном refresh после возврата в окно сессия удаляется, закрывается приватный экран, очищается storage; перезагрузка между отказом и очисткой не требуется. Серверная проверка `exp` покрыта отдельным тестом выше.
- На облаке проверены реальный TTL, подпись, refresh и отзыв refresh. Проверка **правильно подписанного expired JWT** выполнена на локальном Supabase, а не выдана за отдельный облачный тест.

**Ограничения:** уже выданные до изменения настроек токены сохраняют прежний `exp`; настройка не переписывает их. После logout access JWT может оставаться действительным до `exp`: немедленный серверный denylist/session lookup не добавлен. Сама сессия может продлеваться при действительном refresh; абсолютный срок сессии и inactivity timeout не настроены. Политика 15 минут относится к отдельному access-токену. Подробнее: [сессии Supabase](https://supabase.com/docs/guides/auth/sessions), [выход](https://supabase.com/docs/guides/auth/signout).

## SQL-инъекции и права

SQL-функции используют статические запросы и типизированные параметры. Конкатенации пользовательского ввода в исполняемый SQL, динамического `EXECUTE` и произвольного SQL endpoint в приложении нет. Данные передаются через PostgREST/RPC параметрами; удалять кавычки из пользовательского текста для защиты не требуется. Подход соответствует [рекомендациям OWASP по параметризации](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).

Проверено через реальный API локально и в облаке:

1. Строки `' OR '1'='1` и `x'); SELECT current_user; --` сохраняются дословно в названии/описании. Не исполняются как SQL.
2. REST-фильтр равенства по такому названию возвращает только соответствующую строку; второй исполнитель не видит её.
3. Инъекция в UUID-параметр `update_task` отклоняется HTTP 400, название и версия задачи не меняются.
4. Запись `role: manager` в редактируемые метаданные Auth не меняет роль в `profiles`; менеджерский RPC для исполнителя остаётся запрещённым. Метаданные после проверки восстановлены.
5. Существующие 60 PostgreSQL-тестов проверяют RLS, матрицу переходов, запреты прямой записи и подделки истории. Функции `SECURITY DEFINER` имеют пустой `search_path`, квалифицированные имена таблиц и явно ограниченные права EXECUTE.

Тесты используют временные данные и безвредные SQL-подобные строки; команды удаления таблиц, слепые длительные задержки и внешние callback-запросы не запускаются. Это целевое подтверждение механизмов защиты, а не полный набор возможных SQLi-payload.

## Дополнительное укрепление

- Минимальная длина пароля в облаке приведена к локальным 12 символам. Открытая регистрация и anonymous signup остаются отключёнными.
- Отключено принятие сессии из URL (`detectSessionInUrl: false`): приложение использует только вход по email/паролю, OAuth/magic link не реализованы.
- В production-сборку добавлен CSP: скрипты только со своего origin, соединения только со своим origin и настроенным Supabase; запрещены плагины и чужой base URL. Inline-стили разрешены для UI-библиотеки, inline-скрипты и `eval` — нет. Dev-сервер этим production-правилом не ограничивается.
- React выводит пользовательский HTML как текст. Браузерная регрессия с `<img ... onerror=...>` проверяет отсутствие созданного изображения и исполнения обработчика.
- Исправлено наследование заголовков nginx: `add_header` в location ранее перекрывал security-заголовки уровня server; нужные заголовки теперь явно заданы и для HTML, и для assets.
- Сканер секретов проверяет отслеживаемые файлы и сборку; административные ключи не добавлялись в клиент или Git.

## Воспроизведение и границы

```bash
npm run test:security       # настоящий локальный Supabase + Docker
npm run test:e2e            # теперь 12 браузерных сценариев
node scripts/check-production-security.mjs # после build + preview на порту 4174

# PowerShell: отдельный облачный запуск API-проверок
$env:SECURITY_ENV_FILE='.env.access'
npm run test:security -- --remote
Remove-Item Env:SECURITY_ENV_FILE
```

API-проверки включены в CI после локального seed. Локальный тест ожидает контейнер `supabase_auth_construction-crm` и текущий алгоритм ES256; если схема ключей изменится, тест завершится ошибкой, а не молча пропустит проверку срока.

Фактический результат: 7/7 групп API-проверок локально, 6/6 в облаке (отличие — проверка подписи expired JWT). Все 12 Playwright-сценариев прошли на собранном production-фронтенде с облачной базой. Отдельный браузерный тест CSP подтвердил блокировку внедрённого inline-script событием `securitypolicyviolation` и отсутствие его выполнения. В запущенном nginx проверены `nosniff`, `DENY` и Referrer-Policy на `/` и реальном JS asset. Для проверки CSP по публичному URL задайте `SECURITY_APP_URL`.

Отчёты без секретов: [security-results.json](security-results.json); сырые локальные файлы — `artifacts/security-*.json`.

Токены SPA хранятся в localStorage и доступны JavaScript того же origin; CSP и экранирование снижают XSS-риск, но не делают хранилище HttpOnly. Для иной модели безопасности потребуется backend/BFF. GitHub Pages не позволяет приложению задать произвольные HTTP security-заголовки: CSP здесь передаётся через meta; `frame-ancestors`/X-Frame-Options для Pages не заявлены. Docker/nginx имеет X-Frame-Options. MFA, CAPTCHA, внешний DAST, supply-chain-аудит всех инструментов, немедленный отзыв access JWT и проверка браузерных расширений не выполнялись/не добавлялись.
